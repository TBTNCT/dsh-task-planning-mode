# 规划文档骨架（5 类）

本 skill 是「任务规划」模式的**模板库**。它的唯一作用是：让同一份规划两次跑出来的文件名与章节一致。

## 一、什么时候用、怎么用

1. **产出任何规划文档之前，先加载本 skill 取骨架。** 顺序是：加载本 skill → 选对应骨架 → 把 `<…>` 占位符换成项目自己的词 → 再落盘。
2. **【必须】章节不得删减**；**【可选】章节**可以省略，但要在给使用者的回复里**说明为什么省略**（例如「本项目没有插件，所以没产出插件提示词」）。
3. **骨架里的 `<…>` 一律要替换**，不许原样留在交付物里；也不许写「参见上文」「按需调整」「此处略」这类空话。
4. 不要把本 skill 的正文整段复述给使用者；它只是骨架来源，交付物才是产出。
5. 五类骨架与目标文件一一对应：

| 骨架 | 目标文件（工作区内相对路径） | 谁读它 |
|---|---|---|
| 一、总览与使用说明 | `docs/工作流程/00-总览与使用说明.md` | 使用者第一眼看的门面 |
| 二、任务文件 | `docs/工作流程/NN-<短语>.md`（一个任务一个文件） | 执行任务的另一个对话 |
| 三、通用规范 | `docs/优化提示词/01-通用规范.md` | 每个任务开工前都读 |
| 四、执行进度台账 | `docs/优化提示词/执行进度.md` | 跨会话的唯一状态真相 |
| 五、验收报告 | `docs/验收报告/NN-报告.md` | 人工验收与后续任务查证 |

6. **验收报告什么时候产出（这条决定"两次运行产出的文件集合"是否一致，务必照做）**：
   - **规划阶段**：只给**验收门任务**（编号 `90` 之类、或总览里标注为「门」的那一个）**预写一份报告骨架**到 `docs/验收报告/NN-报告.md`，里面**所有结论一律留空标 `⬜ 待回填`**，**禁止提前填 ✅/❌**；
   - **其余任务**的报告在该任务**执行时**产出，规划阶段**不预写**；
   - 于是每次规划产出的文件集合是确定的：**总览 + 任务文件 + 通用规范 + 执行进度台账 + 一份门的验收报告**。
   - 若本项目没有验收门任务，就不产出验收报告，并在回复里说明「本项目无验收门，故无预写报告」。

## 二、五类骨架共用的硬规则

1. **编号即执行顺序**：两位数字前缀（`00`/`01`/`02`/`10`/`20`/`90`…），同一目录内从小到大就是从先到后。`00` 留给总览与使用说明，**它不是任务**。
2. **文件名骨架 = `<编号>-<短语>.md`**：编号与短语之间是**一个半角连字符**；短语 2–12 字，直白说清「做什么」，**不写「任务」「文档」这类赘词**；文件名与文件里的 H1 标题互为展开，不做两套说法。
   **编号一律两位、带前导零，且文件名里的编号与 H1 里的编号必须逐字一致**：`01-计时核心与菜单.md` ↔ `# 任务 01：计时核心与菜单`（**不是** `# 任务 1：`）；`90-端到端验收.md` ↔ `# 任务 90：端到端验收`。
3. **插入任务用字母后缀**（`03A-<短语>.md`），插在母号之后，**绝不重排已有编号**。
4. **一个任务 = 一个文件 = 一次新对话**；任务文件里必须有一段**能整段复制**的提示词。
5. **任务文件的信息头是 5 个字段、顺序固定**：阶段 / 前置任务 / 建议同时提供 / 本任务产出 / 对话方式。
6. **提示词块内是 5 个固定小标题、顺序固定**：【项目背景】【已知现场】【本任务要做的事】【硬性要求（不可退让）】【本段验收目标】。
7. **验收标准一律用复选框** `- [ ]`，每条都能让使用者点几下就验证。
8. **台账五态标记只有这五个**：`⬜ 未开始` · `🔄 进行中` · `✅ 完成` · `⏸️ 阻塞（等人工）` · `↩️ 返工`；**台账表头固定 6 列**：任务 | 名称 | 状态 | 提交哈希 | 关键数据 | 验收。
9. **报告必须有证据**：结论用 `✅`/`⚠️`/`❌`，证据给到 `文件:行号` 或命令与数字。
10. **每任务收尾四步**：提交 → 回写台账本任务一行 → 写验收报告 → 标了「验收门」的停下等人工。
11. **并行必须收口**：允许把互不依赖的任务标成「可并行」，但必须同时满足三条——
    ① 并行任务**改的文件/目录互不重叠**（会碰同一个文件的，一律串行）；
    ② 总览的版本依赖图里**画出并行分支**；
    ③ **单列一个「组装验收」任务**排在这批并行任务之后，负责合并冲突、接口对齐、重复实现、
    各自验收相互抵消的检查。**缺 ③ 就视为规划不合格。**

````markdown
## 一、这套文件是什么

1. <数据驱动：内容放数据文件，逻辑放代码，不硬编码>

4. <只读数据文件不得改写或删除已有条目，只新增>
5. <不省略代码：禁止「此处略」「按需调整」>
````

**目标文件**：`docs/工作流程/NN-<短语>.md`（**文件名里不写「任务」二字**）

| 章节 | 必须? | 作用 |
|---|---|---|

| 二、开场准备 | 【必须】 | 确认前置 → 新建对话 → 读不到工作区就拖哪些文件 → 只读文件禁令 |
| 三、提示词（复制以下整段） | 【必须】 | **唯一**的代码块，块内 5 个【】小标题 |
| 四、验收标准 | 【必须】 | `- [ ]` 复选框 |

提示词块内 5 个小标题的分工：

| 小标题 | 写什么 |
|---|---|
| 【项目背景】 | 一句话现状 + 为什么现在做这一步 |
| 【已知现场】 | 第一步读哪些文件（工作区内相对路径）；待改点 `<file>` 与现状；明确不在本任务范围内的边界 |
| 【本任务要做的事】 | 逐条编号，说清做什么、做到什么程度 |
| 【硬性要求（不可退让）】 | 编号的量化判据 + **负面清单**（不许做什么）+ 提交/交付要求 |
| 【本段验收目标】 | 一句话、可判定的判据；末尾固定写「最后告诉我人工如何验收。」 |

> **发布类项目的额外要求**：最终程序要开源 / 要发布时，规划里必须多出一个**「开源前隐私检查」任务**，
> 排在发布任务之前（作为发布的门）。该任务的【硬性要求】必须含这几条可验收判据：
> 「工作区 + 全部提交历史双扫」「统一占位符约定」「截图 / 图片 / 二进制人工过一遍」
> 「发现真凭据先吊销再清理」「block 级命中 0 且内部产物未被 git 跟踪」。

## 骨架三：通用规范

**目标文件**：`docs/优化提示词/01-通用规范.md`（**每个任务开工前必读的公共底座**）

| 章节 | 必须? | 作用 |
|---|---|---|
| H1 + 引用块（这是什么 / 阅读顺序 / 用户补充区在哪） | 【必须】 | 说明文件地位与读法 |
| 一、你在做什么 | 【必须】 | 一段话说清项目定位与交付物 |
| 二、铁律（违反任何一条 = 本次执行失败） | 【必须】 | 编号清单，每条可判定 |
| 三、验证手段（按优先级使用） | 【必须】 | 先自检脚本、再端到端、最后人工点验 |
| 四、关键技术事实速查 | 【必须】 | 表：子系统 / 位置 `file:line` / 现状 |
| 五、收尾四步 | 【必须】 | 提交 → 回写台账 → 写报告 → 有门就停 |
| 六、针对执行模型的特别提醒 | 【必须】 | 不复述任务、不为凑验收削弱测试、失败即停 |
| 七、用户补充区 | 【必须】 | 留空位给使用者追加项目特有规则 |
| 环境特殊性（shell/文件系统/包管理器来源） | 【可选】 | 按**检测结果**写，不预设具体值 |
| 开源前隐私门（**仅当最终程序要开源**） | 【必须】 | 工作区 + 历史双扫、五类检查、占位符约定、「先吊销再清理」、block 命中 0 |

````markdown
# 01-通用规范（铁律 · 每个任务开工前必读）

> 本文件是《<项目名>》所有任务的公共约束，无论你是什么模型，规则一视同仁。
> 每次会话执行任务时：**先读本文件 → 再读任务文件 → 最后动手。**
> 用户补充区在文末，可追加项目特有规则；补充规则与铁律冲突时以铁律为准。

## 一、你在做什么

<一段话说清项目定位、使用者是谁、本项目的交付物有哪些。>

## 二、铁律（违反任何一条 = 本次执行失败）

1. **范围围栏**：只做任务文件里列出的事；发现相邻问题（bug、坏味道、「顺手就能改」）→ 写进报告，不许改。
2. **先读后改**：改任何文件前先读它；禁止凭记忆猜接口、字段与配置名，一切以本仓库现状为准。
3. **一步一验**：每个可独立验证的步骤做完立刻验证；失败即停、如实报告，**禁止放宽验收标准**。
4. **数字说话**：所有「能用 / 更快 / 更省」的结论都要附证据（命令与输出、`文件:行号`）。
5. **只读文件不得改写**：`<列出只读文件>` 只读，只新增条目或新建文件，不删改已有内容。
6. **不省略代码**：禁止「此处略」「按需调整」。
7. **提交格式**：`[<前缀>] <说明>`；一个任务一次提交（或按原子步骤多次，每次都要是「能跑」的状态）。
8. **失败即停**：同一个错误试 3 次仍失败 → 记录现场，交人工裁决。
9. **文档语言**：所有新增文档、注释、报告一律中文。
10. **人工验证边界**：凡需要「新开会话 / 重启 / 在界面里点选 / 在浏览器里操作」的验证，**一律由人工执行**；
    AI 只给精确步骤，等人工回填**原始输出**后如实写入，**禁止推测或「合理补全」**。
11. **开源前隐私门**：本项目的最终程序**只要有开源需求**，**发布之前**必须过隐私门——
    ① 工作区与**全部提交历史**双向扫描（只删最新提交不算过；提交历史的作者 / 提交者身份也算公开内容）；
    ② 真实姓名、登录用户名、邮箱、机器 SID、家目录与内网绝对路径、各类凭据，一律占位化或清除；
    ③ 扫描器扫不到的截图 / 图片 / 二进制 / 文档属性必须**人工过一遍**；
    ④ 发现真凭据：**先吊销，再清理**（清历史不能替代吊销，对方可能早已 clone）。
    **个人签名允许但不强制**；使用者没有明确要公开的署名时，用中性署名（如 `<项目名> contributors`）。
````

## 三、落盘前的 11 条核对（逐条给出结论）

1. **文件名合规**：`00-总览与使用说明.md`、`NN-<短语>.md`（无「任务」二字）、`01-通用规范.md`、`执行进度.md`、`NN-报告.md`。
   **且 H1 里的编号与文件名前缀逐字一致（含前导零）**：`01-<短语>.md` ↔ `# 任务 01：<短语>`。
2. **编号即顺序**，插入件用字母后缀，**没有重排已有编号**；**总览里有「版本迭代规划」小节**
   （版本表 + 版本依赖图 + 并行说明），且**每个并行批次后面都有一个「组装验收」任务**。
3. **每个任务文件都有 5 字段信息头**与**五节正文**，提示词块内 5 个【】小标题齐全、顺序一致。
4. **提示词块能整段复制**：第一人称、第一步读文件、含负面清单、结尾写「最后告诉我人工如何验收。」。
5. **验收标准是复选框**，每条都能点几下验证。
6. **台账表头是 6 列**、状态只用五态标记；「验收」列留给人工。
7. **【必须】章节没被删减**；省略了哪个【可选】章节，**已说明原因**。
8. **没有空话**：全文搜不到「参见上文」「按需调整」「此处略」「视情况而定」。
9. **验收报告按第 6 条口径产出**：有验收门任务时，`docs/验收报告/NN-报告.md` 已预写且**结论全是 `⬜ 待回填`**；无门则说明「无验收门，故不产出」。
10. **开源需求是否落到规划里**：使用者提了要开源 / 要发布时，规划里**是否有一个「开源前隐私检查」任务**，
    且位置在**发布任务之前**、提示词含「工作区 + 全部提交历史双扫」与「block 级命中 0」判据？
    （使用者没提开源就不强制，但要在回复里问一句「这个项目要不要开源」。）
11. **版本迭代是否落到规划里**：使用者确认过的那张**版本迭代规划表**，是否**原样落盘**进总览的
    「版本迭代规划」小节（版本表 + 版本依赖图 + 并行说明三件齐全）？每个任务文件信息头的「阶段」
    是否都填了对应版本号？**有没有标了「可并行」却没有「组装验收」任务的并行批次**？（有 = 不合格）
