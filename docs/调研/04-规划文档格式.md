### A.3 命名里「编号-短语.md」的写法规律

1. **骨架固定**：`<编号>-<短语>.md`，编号与短语之间是**一个半角连字符**；短语内部**不用空格**（连续中文，必要时再用 `-` 连接），例如 `T16-P0.4a1-收口正式化与分片映射.md`。
2. **短语 = 内容摘要**，2~12 字，直白说清"做什么"，不写"任务/Task/文档"等赘词（性能线例外：文件里保留 `T*` 编号前缀）。
3. **文件名与 H1 标题互为展开**，不做两套说法：`54-T3-T6科技激活.md` ↔ `# 任务 54：T3~T6 科技激活`（54:1）；`70-最终验收与发布.md` ↔ `# 任务 70：最终验收与发布报告`（70:1）。
4. **一任务多产出用后缀区分**，前缀保持一致：`-报告` / `-报告-批次二` / `-报告-收尾` / `-会话交接` / `-耦合边界表`。
5. **机器读数与报告同前缀**，靠扩展名区分：`性能T14-parity-p0-step0.25.json` 对应 `性能T14-报告.md`。
6. **字母后缀不重排原编号**：`26 → 26A → 26B → 27`、`53 → 53A`、`62 → 62A → 62B/62C → 63`，所以「编号大小 ≈ 执行顺序」在字母后缀上依然成立（工作流程\00:195-198 的依赖串）。
7. **版本子目录 = 阶段版本号**（`v0.8`/`v0.9a`/`v0.9b`/`v0.10`），与文档自身版本号（`v1.0`/`v2.0`）**是两码事**；派生任务可跨目录（T15.5 是 v0.9b 裁定派生，却放在 `v0.10/`，README.md:23,58）。
8. **一个编号一条台账行**：台账行首编号必须能反查到同名任务文件（见 E 节）。

## B. 每类文件的内容骨架

> 标注口径：**【必须】**= 缺了这类文件就不成立（其他任务/另一个对话读不到关键信息）；**【可选】**= 规模变大或遇到对应场景才加。
> 每个骨架都是**可直接复制的 Markdown**，把 `<…>` 换成项目自己的词即可。

### B.1 工作流程任务文件（主开发线的一个任务）

章节清单（证据：`工作流程\54-T3-T6科技激活.md`）

| 章节 | 必须? | 作用 / 写法要点 |
|---|---|---|
| H1「任务 N：短语」 | 必须 | 与文件名互证（54:1） |
| 引用块信息头（阶段/前置任务/建议同时提供/本任务产出/对话方式） | 必须 | 五个字段固定顺序（54:3-7），见 C 节 |
| `## 一、任务目标` | 必须 | 3~6 行说清"这一步做出什么"（54:11-13） |
| `## 二、开场准备` | 必须 | 编号步骤：确认前置任务 → **新建对话** → 读不到工作区就拖哪些文件 → 只读文件禁令（54:15-20） |
| `## 三、提示词（复制以下整段）` | 必须 | **唯一的代码块**，整段可复制（54:22-68） |

### B.3 会话交接文件

用途：**一个任务跨多对话时，让新对话从零接手**。放在提示词目录**顶层**（`优化提示词\T14-会话交接.md`），命名 = `T<任务号>-会话交接.md`。

| 章节 | 必须? | 作用 / 写法要点 |
|---|---|---|
| H1「性能任务 T<N> 会话交接（<日期>）」 | 必须 | T14-会话交接:1 |

## D. 提示词文件的写法特征

### D.1 它是什么：**给"另一个对话"的指令书**，不是设计文档

判断依据（全部来自原文）：

| 特征 | 证据 |
|---|---|
| 文件里有一段**独立、可整段复制**的提示词代码块，其余章节都是给人看的说明 | 工作流程\54:22「`## 三、提示词（复制以下整段）`」；README.md:11「把「三、提示词」的代码块整段复制发送」 |
| 提示词以**第二人称命令式**写给 AI，且第一步永远是"读文件" | T16-P0.3a:45-48「第一步：读 docs/优化提示词/00-通用规范.md、…（**机器系统的节是主依据；与本文"已知现场"冲突时以边界表为准，并把差异回写本文件**）…读不到就让我拖进对话」 |
| 面向"几乎没有编程基础"的用户，AI 负责全部代码 | T16-P0.3a:37「我几乎没有编程基础，全程由你生成代码。所有代码注释用中文。」；v0.8\T1:24 同句 |
| 结尾必须**交代人工怎么验收** | T16-P0.3a:71「最后告诉我人工如何验收。」 |
| 设计与数值**不在提示词里定义**，只引用权威文档 | 00A:254「数值的唯一来源是 01/02/03 三份设计文档…本台账只做"有没有、归谁做"」；README.md:15「每个提示词的第一步都会要求 AI 先读 docs/优化提示词/00-通用规范.md…这是所有任务共享的公共底座」 |

|---|---|---|---|

### E.2 谁在什么时候写：任务收尾的固定四步

`docs\优化提示词\00-通用规范.md:54-59`（原样照录，节选）：

```
## 五、报告与进度（每任务完成的收尾动作）

1. **提交**：按铁律 7 的格式 commit。
2. **回写进度**：更新 `docs/优化提示词/执行进度.md` 中本任务一行（状态、提交哈希、关键数据）。
3. **任务报告**：写入 `docs/验收报告/性能T-x-报告.md`，包含：做了什么（含偏离计划之处）、验证结果（测试清单+结果）、性能数据（前后对比表）、遗留问题/给下一个任务的注意事项。
```

## F. 一句话结论：这套格式的「最小可用子集」

> **一句话**：新项目从零开始时，只需要 **「1 份总纲 + 1 份任务总览 + 1 个公共规范 + 1 张进度表 + 每个任务 1 个任务文件 + 每个任务 1 份验收报告」** 这 6 类东西就能跑通；台账、会话交接、门报告、自检域索引、决策日志都是规模变大后自然长出来的增量，不是起步必需。

| 最小文件（相对 `docs\`） | 对应样板 | 为什么必须有 |
|---|---|---|
| `最终总体规划.md` | `docs\最终总体规划.md` | 所有任务的第一顺位参考资料；数值/结构的权威指针（44:最终总体规划.md:7） |
| `工作流程\00-总览与使用说明.md` | `docs\工作流程\00-总览与使用说明.md` | 任务清单 + 执行顺序 + 通用约定（铁律），否则不知道下一个做哪个 |
| `优化提示词\00-通用规范.md` | `docs\优化提示词\00-通用规范.md` | 每个提示词第一步都要读的公共底座（铁律/验证手段/收尾动作）——**这条是整套格式的关键**（README.md:15） |
| `优化提示词\执行进度.md` | `docs\优化提示词\执行进度.md` | 唯一的跨会话状态真相；回写规则见 E 节 |
| `工作流程\<NN>-<短语>.md`（每任务一个） | `docs\工作流程\54-T3-T6科技激活.md` | 任务文件本身（信息头 + 提示词 + 验收标准 + 常见问题） |
| `验收报告\<NN>-<短语>报告.md`（每任务一个） | `docs\验收报告\54-…报告.md` | 给人工验收与后续任务查证的结论 + 证据 |

**起步骨架（把下面这段改词即可，6 个文件共用同一套"信息头 + 结论 + 证据"哲学）：**

```markdown
# 《<项目名>》最终总体规划（MASTER PLAN）
```

## 附：新项目落地这套格式的 10 条硬规则（可直接当检查清单）

1. **一个任务 = 一个文件 = 一次新对话**；文件里必须有一段能整段复制的提示词（工作流程\00:16-24）。
2. **编号即顺序**：主干 `01..NN` 顺序执行；插入件用字母后缀（`26A`、`54A`），**永不重排既有编号**（工作流程\00:13-15）。
3. **两条线各自编号系**：业务线 `01~NN`，性能/内核线 `T*`，互不占用。
4. **文件名 = `<编号>-<短语>.md`**，与 H1 标题互证；改任务先改文件与总览索引，再改提示词（工作流程\00:238）。
5. **信息头字段顺序固定**（阶段/前置/（门）/建议同时提供/产出/对话方式/（难度）），缺字段视为不合格。
6. **提示词是"给另一个对话的指令书"**：第一人称、第一步读文件、硬性要求编号、禁止清单、提交格式、结尾交代人工验收。
7. **每个任务收尾四步**：提交 → 回写进度台账 → 写验收报告 → 有门就停下等人工（00-通用规范.md:56-59）。
8. **报告必须有 file:line / 自检编号级证据**，结论先行（✅/⚠️），改动清单末尾声明只读文件的 `git diff` 为空。
9. **遗留必须分类登记**（致命/一般/建议 或【遗留·非本任务】），并写清"谁在什么时候处理"。
10. **跨会话靠文档不靠记忆**：新对话的上下文 = 总纲 + 公共规范 + 本任务文件 + 执行进度.md（+「开工前必读」条目号）；换模型时同一提示词可直接重试（README.md:41）。
