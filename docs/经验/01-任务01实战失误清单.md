## 一、十条失误（按"教训可迁移性"排序，E1 最贵）

### E1　调研文档没有锁定"运行中的那一份"（最贵）

- **现象**：严格按 `docs/调研/01-preset机制.md` 做的 preset 目录，文件对、位置对、时间对、也重启了，
  模式选择器里**始终没有**。
- **证据**：调研依据的是 `<DSH_INSTALL>\node_modules\@deepseek-ai\dsh-agent-presets@0.1.5-rc.2`；
  而桌面端宿主命令行指向 `…\resources\app.asar\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\index.js`，
  实际加载的是 asar 里 `dsh-web-app@0.2.1-alpha.1` 的**声明式 preset**
  （`@deepseek-ai/dsh-agent-preset` + `dsh-agent-preset-registry`，**不扫描任何目录**）。
- **根因**：调研只看了"安装目录里存在的包"，**没有确认运行进程真正加载的是哪一份**。
- **教训**：同一台机器可以并存多份同名不同版本的运行时树（安装 asar / `<DSH_INSTALL>` / profile `node_modules`）；
  任何机制结论都必须绑定「哪个进程 + 哪份文件 + 什么版本」。
- **模式约束建议**：规划第一步强制输出**运行版本锁定表**（进程 → 实际加载路径 → 版本 → 证据命令）；
  机制结论一律注明证据来源文件与版本，跨版本处标"未验证"。

### E2　用"文件级校验"冒充"端到端可用"

- **现象**：机器校验 34/34 PASS（YAML 形状、包名可解析、字节一致），但模式从未出现；
  而且我一度把人工验证第 3 项当成"等回填"，而不是"已失败"。
- **根因**：发现阶段不 import（旧文档 F.1）——**"配置合法"≠"能加载"**；校验器只验文件，不验运行。
- **教训**：验收标准必须包含**用户可见的最终效果**；文件级校验不能单独判过。
- **模式约束建议**：每个任务的验收表强制含一行「用户可见效果」（谁 / 在哪 / 看到什么），
  并写明"文件级校验不得单独作为通过依据"。

### E3　用"自造的等价检查"代替"运行方自己的工具"

- **现象**：我用第三方 YAML 库 + 自定规则判"preset 合法"，结论虽对，却**证明不了**运行方会接受它。
- **证据**：真正定案的两件事是——① 安装树里逐包的 `Config = z.object({…})` schema；
  ② 界面给出的报错原文（见 E4、E5）。
- **教训**：验证手段要与"判定者"同源。
- **模式约束建议**：验证优先级写死：① 运行方自带 CLI/RPC/UI → ② 运行方源码里的 schema/校验函数 →
  ③ 自造脚本（只作补充，且报告里必须标注"非运行方口径"）。

### E4　把"新版本的必填字段"当成"旧版本的可选项"

- **现象**：preset 出现在「设置 → Agent presets」的**自定义分组里**，但带红色「加载失败」，模式选择器里看不到。
- **证据**（人工截图 + 安装树源码）：
  ```text
  tool-fs-search (@deepseek-ai/dsh-tool-fs-search): invalid config:
  - $.sampleOverCapGlobResults missing required value (at sampleOverCapGlobResults)
  ```
  `…/dsh-tool-fs-search/lib/index.js:1218` 为 `z.boolean().required()`；而 0.1.5 时代它只是可选。
- **根因**：跨版本抄配置；"可选 → 必填"是常见的破坏性变更。
- **模式约束建议**：凡涉及配置/接口字段，规划里必须写「依据版本 + 该字段在该版本的必填/可选 + 证据位置」，
  并规定"改字段前先读目标版本的 schema"。
- **闭环**（2026-10-12 13:20）：补上该字段 + 重启后，人工确认「新模式已出现」；
  机器佐证：空白会话 `session-48bfd263` 的 `agentPreset` 投影由 `standard` 变为 `task-planning`。
  → 这条经验的价值已被验证：**一个必填字段就能让整个模式"存在但不可用"**。

### E5　原始报错拿得太晚

- **现象**：从"选择器里没有"出发，走了选择器 → 进程命令行 → 解 asar → dump-config 一大圈；
  最后是**用户截图里的一句悬浮提示**定案。
- **教训**：界面/日志给的**原始报错**，信息密度远高于任何侧写推导。
- **模式约束建议**：排错**第一步**就是索取原始报错原文（界面提示 / 日志 / 退出码）；
  "没有原始报错的推断"只能记为假设，不得据此改文件。

### E6　环境前提没有前置检查（工作区 / 盘符 / 权限 / 包管理器）

- **现象**：会话工作区是 `<OLD_WORKSPACE>`（FAT32，`write` 工具必失败）而任务要求 D:；
  对 D:/C: 的写入被沙箱拒绝（最终靠一次性提权 + 中途改策略完成）；安装插件时又撞上 pnpm store 位置不一致
  （`<DSH_HOME>\.pnpm-store\v11` vs `D:\.pnpm-store\v11`，报 `ERR_PNPM_UNEXPECTED_STORE`）。
- **教训**：**环境前提是任务的一部分**，应当开工即验，而不是做到一半撞墙。
- **模式约束建议**：每个任务开头强制输出**环境预检表**（工作区 / 盘符文件系统 / 权限策略 / 包管理器与 store /
  网络与镜像），任一不合格先解决或明确降级，并写进记录。

### E7　把"安装动作成功"等同于"能力可用"

- **现象 A**：pnpm 日志 `Done in 581ms`、依赖与 `dsh.profile.bundles` 都写入、符号链接也在，模式仍不可用（因 E4）。
- **现象 B**：12:49 那次安装失败**安全回滚**（`package.json` 与 `pnpm-lock.yaml` 逐字恢复）——"失败会留残留"是错觉。
- **模式约束建议**：安装/部署类步骤的验收拆三层：① 产物落地 → ② 运行方加载成功（无 failed 行）→ ③ 用户可见效果；
  三层都过才算过，并核对失败后的残留状态。

### E8　规则的作用范围没写清（模式约束 vs 普通执行）

- **现象**：需要专门补充"模式约束只在该模式会话内生效；执行任务时走标准模式；
  模式未装上之前，以本工作区对话充当模式对话"。
- **模式约束建议**：模式系统提示词里必须有**作用范围声明**：本约束只作用于选中本模式的会话；
  跨会话执行任务时按标准模式正常实现。

### E9　临时产物位置与"仓库产物 vs 运行期副本"没定义

- **现象**：为绕开写入限制，内容先在 `%TEMP%` 暂存再提权写入；
  用户层副本（`.agent-presets\...`、profile 依赖）与仓库是**快照关系**，改了仓库不重装就不生效。
- **模式约束建议**：规划里为临时产物指定唯一位置（如 `%TEMP%\<任务名>\`）并在收尾清理；
  明确区分"仓库产物"与"运行期副本/快照"，并写明副本的同步方式。

### E10　修复后过早请人工重试

- **现象**：修完 pnpm store 就请人工重试安装；装成功了却仍卡在 E4，又多一轮往返。
- **教训**：AI 应当把**所有机器可验证的部分**先跑完，只把"只有人能做的动作"交给人工。
- **模式约束建议**：每次请人工验证前，先跑尽可机器验证的自检，并在消息里分列
  「我已自检的项」与「只有你能做的那一步」。

## 二、做对了、要固化的四条

| # | 做对的事 | 为什么有效 | 模式里怎么固化 |
|---|---|---|---|
| G1 | 发现前提冲突后**立即停下上报**（铁律 7），没有硬按旧机制把 8 个后续任务做下去 | 避免整条主线建在错误前提上 | 约束："现实与规划冲突 → 停下 + 出证据 + 给选项，不自行改规划、不硬做" |
| G2 | 原始输出照抄留档（命令、报错、截图、`file:line`） | 第二轮定位（E4）全靠这些记录，几分钟收敛 | 约束："每个结论后附可重放命令与原始输出，禁止'已验证'式断言" |
| G3 | 不猜 API，先读运行方源码与官方 README | 一步定死"注册表不扫描目录""必填字段" | 约束："配置/字段/服务名一律以目标版本源码或官方 README 为准" |
| G4 | 严守 AI / 人工边界（铁律 11），不代填界面结果 | 用户截图直接成为定案证据 | 约束："需新开会话/点界面/重启的验证只能由人做；AI 只给步骤并照抄回填" |

## 三、可直接供任务 04 取用的「硬约束候选」12 条

> 任务 04 出稿时把这 12 条**改写成与机器无关的通用措辞**再并入系统提示词；本清单本身不整段粘贴。

1. 开工先出**运行版本锁定表**（进程 → 实际加载物 → 版本 → 证据）与**环境预检表**（工作区/权限/包管理器/网络）。
2. 一切机制结论标注**证据来源文件与版本**；跨版本结论必须标"未验证"。
3. 验收表必须含一行「**用户可见效果**」；文件级校验不得单独判定通过。
4. 验证优先用**运行方自带**的 CLI/RPC/UI，其次运行方源码里的 schema/校验函数，自造脚本只作补充。
5. 涉及配置或接口字段时，写清**该版本的必填/可选**与证据位置；改字段前先读目标版本 schema。
6. 排错第一步索取**原始报错原文**；无原文的推断只能记为假设，不得据此改文件。
7. 安装/部署类步骤按**三层**验收：产物落地 → 运行方加载成功 → 用户可见效果；并核对失败残留。
8. 临时产物放**指定临时目录**并在收尾清理；明确"仓库产物 vs 运行期副本"及同步方式。
9. 每轮请人工验证前，先耗尽机器可验证部分，并分列「已自检项」与「仅人工项」。
10. 前提与规划冲突时**停下 + 证据 + 选项**，不自行改规划、不硬做。
11. 输出**作用范围声明**：本模式的约束只作用于选中本模式的会话，其它会话按标准模式正常实现。
12. 结论只认**产出物与证据**，不认自述（沿用铁律 4 与铁律 11）。

## 四、这次实践对"规划质量"的三点元观察

1. **最大的浪费不是写错文件，而是没锁定前提**：E1 一旦发生，后面所有"照着文档做"的努力都会白做。
   规划的价值，首先是**把前提钉死**。
2. **可见性 > 正确性**：模式"注册成功但加载失败"这种状态，只有用户界面能一眼看清；
   规划里要主动定义"怎么让失败可见"，而不是只定义"怎么算成功"。
3. **经验必须回流成约束**：这次 10 条失误里，只有 E4/E6 是纯技术细节；
   其余 8 条都是**流程约束**问题——正好说明这个模式的系统提示词应当以"约束"为主体，而不是以"步骤"为主体。
