## 一、本次失误（按代价排序）

### F3　用**真实目标**试跑删除脚本，把使用者的目录删掉了（最贵）

- **现象**：为验证 `uninstall.ps1` 的 `-Confirm:$false` 参数是否可用，直接对**默认目标**
  （`%USERPROFILE%\.dsh\.agent-presets\task-planning`）跑了一次。脚本按设计执行了删除——
  **那个目录真的没了**。
- **证据**（原始命令）：
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -Command "& '.\uninstall.ps1' -Confirm:`$false"
  # → exit 0，输出尾部为脚本正常结束块；随后 Test-Path 目标 → False
  ```
- **影响评估（如实记录）**：
  - 被删的是 **0.1.x 旧机制的用户层副本**，在 0.2.x 上**是死数据**（注册表不扫描目录，永远不会出现在模式选择器里，
    证据 `docs/实施记录/01-预设机制冲突-运行时版本不符.md`）→ **功能无损失**。
  - 但它是任务 01 的安装产物、且被 `docs/验收报告/01-报告.md` 记录为"本次新建"的证据 → **证据链断了一环**。
  - 已用 `install.ps1 -LegacyCopy -Force` **从仓库源重建**：目录回来了，2 个文件（`agent.cordis.yml` 3194 B、
    `preset.yml` 426 B）。
  - **重建件与原始件不完全一致**：任务 01 记录的是 `agent.cordis.yml` 2970 B（2026-10-12 创建时快照），
    重建件取自**当前仓库源**（3194 B，后续任务改过）。**这是刻意选择**：宁可与仓库同步，也不要伪造旧快照。
- **根因**：验证"这个脚本能不能删"时，脑子里只有"脚本逻辑对不对"，**没有先问"它删的是谁"**。
  破坏性脚本的默认目标就是使用者的真实环境，而我把它当成了测试夹具。
- **教训**：**破坏性操作（删除 / 覆盖 / 重命名）的首次试跑，必须先把目标指向沙箱**；
  真实目标只允许在"已经确认逻辑正确"之后、且由使用者本人执行。
- **模式约束建议（进提示词候选）**：
  1. 凡是**删除 / 覆盖 / 移动**类脚本或命令，**第一次试跑一律用沙箱目标**（临时目录 / `-DshHome <临时>` /
     显式传入的假路径），**禁止用默认目标或真实路径做首次验证**；
  2. 脚本必须支持 `-WhatIf`，且**默认打印将被影响的确切绝对路径**再动手；
  3. 报告里必须区分「我验证过的」与「我动过使用者的东西」——后者要单列一行如实交代。

### F1　含中文的 `.ps1` 存成无 BOM 的 UTF-8，PowerShell 5.1 直接语法错误

- **现象**：`install.ps1` / `uninstall.ps1` 用编辑器写入（UTF-8 **无 BOM**），
  用 `powershell -File` 跑 → **一堆语法错误**：`Unexpected token 'DSH' in expression`、
  `The string is missing the terminator: "`。控制台里中文显示成乱码（`鐜锛?`）。
- **证据**（原始输出）：
  ```text
  At install.ps1:78 char:24
  +     Write-Host ("[2/3] DSH 鐜锛氭壘鍒?profile -> {0}" -f ($profiles -joi ...
  Unexpected token 'DSH' in expression or statement.
  The string is missing the terminator: ".
  ```
- **根因**：**Windows PowerShell 5.1 读取 `.ps1` 脚本文件时，无 BOM 就按系统 ANSI（本机 GBK）解码**，
  不看内容也不看 `chcp`。UTF-8 的中文字节被当成 GBK 解码后，某些字节恰好落成引号/括号，直接把脚本结构拆坏。
- **处置**：把三个 `.ps1` 全部改存 **UTF-8 with BOM**（`New-Object System.Text.UTF8Encoding($true)`），
  重跑全部通过。
- **教训**：本项目里 **`.md` / `.js` / `.json` 用无 BOM 的 UTF-8，但 `.ps1` 必须带 BOM** ——
  两种约定**方向相反**，不能套用。
- **模式约束建议**：环境预检表里加一行「**交付物含脚本时：该平台的脚本文件编码是什么**」；
  本项目铁律 8 补一条（已补）。

### F2　`$PSCmdlet.ShouldProcess` 在非交互/管道宿主里抛 `NullReferenceException`

- **现象**：`uninstall.ps1` 初版用 `[CmdletBinding(SupportsShouldProcess=$true, ConfirmImpact='High')]`
  + `$PSCmdlet.ShouldProcess(...)`。直接 `powershell -File uninstall.ps1` 跑（宿主 stdio 被管道接管）→
  ```text
  Exception calling "ShouldProcess" with "2" argument(s):
  "Object reference not set to an instance of an object."
  ```
  脚本以退出码 1 中断。
- **根因**：`ShouldProcess` 在 `ConfirmImpact='High'` 时会尝试弹交互确认；**当宿主没有可用的交互控制台**
  （stdio 被重定向 / 非交互）时，确认提示的内部实现拿不到宿主对象 → 空引用。
  它不是"返回 false"，而是**抛异常**。
- **处置**：改成**显式参数** `-WhatIf` / `-Yes` + `Read-Host` 确认；`Read-Host` 拿不到输入时
  用 `try/catch` 兜底成空串 → 走"取消"分支（**失败即安全**）。改后 4 条路径全部实测通过：
  输入 `n` → 取消；输入 `y` → 删除；`-WhatIf` → 只演示；`-Yes` → 跳过确认。
- **教训**：**"优雅的框架特性"在非交互宿主里可能变成硬失败**；破坏性脚本宁可自己写显式确认逻辑，
  也不要依赖宿主提供的确认机制。
- **模式约束建议**：凡是要交给使用者跑（或可能被 CI/管道跑）的脚本，**验收必须包含"非交互路径"**：
  无 stdin、无控制台时也必须有一个明确的、失败即安全的行为。

### F4　扫描器的"豁免白名单"只作用于工作区扫描，历史扫描漏了 → 自己人误报

- **现象**：重写历史后在克隆上复扫，报 `email` 规则命中 2 处，样本是
  `tools/privacy-local-rules.example.json:25: "pattern": "someone@example.com"` 和一处
  `noreply@example.com`。两者**都在 `allow` 白名单里**，本不该报。
- **根因**：`scanWorkingTree` 走 `findInText`（带 allow 判断），而 `scanGitHistory` 的历史 blob 扫描走
  `git grep -P`，**只把匹配行数当作命中数，完全没应用 allow**。同一条规则，两条路径两套语义。
- **处置**：历史扫描改为解析 `git grep` 的 `<commit>:<path>:<lineno>:<content>` 输出，
  **对 content 再跑一次带 allow 的 `findInText`**；修复后 block 命中归 0。
- **教训**：**"豁免 / 白名单 / 忽略"这类逻辑，必须在所有扫描路径上等价生效**；
  否则门禁会变成"狼来了"，用几次就没人看了。
- **模式约束建议**：凡是"检查器 / 校验器 / 门禁"类交付物，验收必须包含**一条"应当被豁免的样本"**，
  证明豁免确实生效（本项目任务 02 的"阳性测试"原则，同样适用于校验器本身）。

3. `%USERPROFILE%\.dsh\.agent-presets\task-planning\` 现在是**重建件**（取自当前仓库源，3194 B），
   与 `docs/验收报告/01-报告.md` 记录的 2970 B 快照不同——引用该目录大小时请注明"重建件"。
4. 隐私门禁跑 `node tools/privacy-scan.mjs`；它的历史扫描与工作区扫描**语义已经对齐**（F4 已修），
