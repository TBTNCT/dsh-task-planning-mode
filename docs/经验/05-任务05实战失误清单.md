## 一、本次失误（按代价排序）

### F1　骨架里写 `<N>` 没规定前导零 → 首轮任务文件 H1 是「任务 1」而不是「任务 01」

- **现象**：首轮 5 个任务文件里，`01-计时核心与菜单.md` 的 H1 是 `# 任务 1：计时核心与菜单`（02/03/04 同病）。
- **证据**（`docs/验收报告/05-自测报告.md` §三 第 7 项 + §四 问题 1）：
  ```text
  FAIL | H1 编号与文件名前缀逐字一致 → 01–04 的 H1 是「# 任务 1：…」（应为「# 任务 01：…」）
  样板：<REFERENCE_PROJECT>\docs\工作流程\01-项目骨架与主循环.md:1 → "# 任务 01：项目骨架与主循环"
  本项目自己：docs\工作流程\01~09 九个文件 H1 全部是「# 任务 01：…」两位补零
  ```
- **根因**：`SKILL.md` 骨架二的 H1 模板写的是 `# 任务 <N>：<短语>`。**`<N>` 是自由占位符**，
  而文件名前缀在规则里被明确要求"两位数字"——**同一个编号在两处、两种写法**，模型两处都"照做了"，结果自相矛盾。
- **教训**：**凡是"同一个值出现在两处"的地方，占位符必须写成同一个形态，并给正反例。**
  `NN` 与 `N` 不是风格差异，是**规范漏洞**：它让"逐字一致"这条要求变成不可判定。
  给反例（`**不是** # 任务 1：`）比只给正例有效得多。
- **模式约束建议**：模板类产物里，**任何"互证关系"（文件名 ↔ H1、台账编号 ↔ 任务文件编号、报告编号 ↔ 任务编号）
  都必须写成"逐字一致（含前导零）"并附一个反例**。

### F2　骨架的「章节表」与「可复制块」自相矛盾（表里有，块里没有）

- **现象**：复测的 `执行进度.md` 引用块只有三行，缺"开工前先看文末的「⚠️ 开工前必读」"；首轮有。
- **证据**（`docs/验收报告/05-自测报告.md` §四 问题 2）：骨架四的**章节表**把
  「引用块：五态标记 legend + 谁回写哪列 + **先看文末**」标成【必须】，但下面**可复制的骨架块里漏了这一行**。
- **根因**：同一份骨架我写了两遍——一遍是**给人看的章节表**，一遍是**给模型抄的代码块**。
  两遍之间**没有一致性检查**，于是"表里有、块里没有"，模型**照块抄**就漏了。
- **教训**：**骨架的"清单"与"可复制块"是同一事实的两种表述，必须逐条对齐**。
  校验时不能只看"关键特征是否存在"（首轮块里有的，复测也都有 → 结构检查全 PASS），
  必须**把章节表的每一条【必须】当成断言，回到可复制块里逐条找**。
- **模式约束建议**：凡"清单 + 模板"成对出现，**落盘前做一次逐条对表**：
  清单里每个【必须】项，都要能在模板块里指出对应行；指不出来的，就是清单或模板错了。

### F3　「验收报告什么时候产出」没定义 → 两次运行产出的文件集合不同

- **现象**：首轮产出了 `docs/验收报告/90-报告.md`（预写的验收表，结论全 `⬜`）；
  复测**一个验收报告都没产出**（把报告安排成任务 90 执行时再写）。
- **证据**（`docs/验收报告/05-自测报告.md` §四 问题 3）：
  - 首轮 `demo/_自测/docs/验收报告/90-报告.md`（7114 B）存在；
  - 复测 `demo/_自测-复测/docs/` 下**没有** `验收报告/` 目录；
  - 而 `PROMPT.md` §十二 自检第 1 条把"验收报告"算进"产出文件是否齐全" → **两轮据此会给出不同结论**。
- **根因**：规格**只说了"要有验收报告"和"报告长什么样"，没说"规划阶段就要有，还是执行任务时才有"**。
  两种理解都合理，模型两次各选了一种。**这不是模型跑偏，是规格留了歧义。**
- **教训**：**"产出物清单"必须带时点**——是"本次会话就要产出"还是"整个项目周期内会产出"。
  凡"某文件由后续任务产生"的，规划阶段要么产出骨架、要么明确说"本阶段不产出"，**不能留空**。
- **模式约束建议**：产出物清单里每一项都标注**产出时点**（本次会话 / 后续任务执行时），
  并对"本次会话"的项做齐全性自检；**跨时点的项要写清落到哪个路径、由谁写**。

### F4　自造校验器把"运行环境假设"藏在了代码里（`ctx.get` 缺失）

- **现象**：第一次跑 `verify-skill.mjs` 时，运行方自带的 `FileSystemSkillProvider` 抛
  `TypeError: ctx.get is not a function`（`optionalFileSystem` 在 `dsh-skill-filesystem/lib/index.js:706` 调 `ctx.get("fs")`）。
- **证据**：`docs/实施记录/05-模板接线记录.md` §4.1（修正后原文）；失败原文见本次会话记录。
- **根因**：我为了"用运行方自带的 provider 做验证"，手搓了一个**假 `ctx`**（只给了 `logger`），
  **没读 provider 到底从 `ctx` 上取哪些东西**。这正好是任务 03 的候选 23（"自造校验器报 FAIL 时先定位是哪一条假设"）
  的**镜像形态**：这次校验器不是"报 FAIL"，而是"**替被测对象假设了一个不完整的运行环境**"。
- **教训**：**用运行方自带组件做验证时，假上下文必须按源码补齐**——先 grep 该组件从 `ctx` 取了什么
  （`ctx.get` / `ctx.logger` / `ctx.effect` …），再构造假 ctx；**缺失时要让它在"服务不存在"的降级分支上跑通**，
  而不是把降级分支当成"用不到"。
- **模式约束建议**：把候选 23 扩写成两条：
  ① 自造校验器报 FAIL 时先定位是哪一条假设（原样）；
  ② **用运行方组件做验证时，先读它从上下文取了什么，把假上下文按源码补齐，并确认走的是"正常路径"而非"降级路径"**。

> **附注（环境前提复发，不算失误但必须记）**：复测会话的工作区 `demo/_自测-复测/` 一度出现
> "缺当前用户完全控制权限"的写入被拒 —— 与本次会话开局时的沙箱 ACL 问题是同一类。
> 处置正确：模式按硬约束 ⑩ 的"环境特殊性处置机制"做了只读检测 + 修复，并把结论写进
> **被规划项目自己的** `01-通用规范.md` §七 用户补充区，备份留在工作区 `acl-recovery/`。
> 教训：**"工作区可写"这个前提每次都要现场验**（候选 16「权限策略时变」的又一次实证）。

## 二、本次做对的事（可复用）

1. **先用运行方自带的解析器/求值器/provider 复现，再下结论**：`loadOverlayPatches` 解析补丁层 →
   `evaluate` 在**真实 `baseUrl`** 下求值 → 官方写法与自写法的**对照实验**（官方写法指向 profile 目录、`存在=false`）。
   这条把"看起来能用的官方写法"证伪得很干脆。
2. **机器侧全绿 ≠ 交付合规**：`validate-bundle` 0 FAIL、skill 结构检查缺失项 0，
   但 H1 那处 ❌ **一条机器校验都查不出来** —— 靠的是**真跑一次 + 逐字比对**。
   "文件级通过 ≠ 能用"这条老结论，在**模板类产物**上表现为"结构全对 ≠ 用起来一致"。
3. **不许放宽判定**：首轮查出 ❌ 后没有"因为它写得不错就算通过"，而是改骨架 + 改提示词 + **复测**，
   并把 ❌ 原样留在报告里。
4. **人工证据不推测**：哨兵值人工第一次答 `v4`（与磁盘 `v5` 不符）时，**没有**挑一个自洽的解释写进报告，
   而是把两种可能分开登记、请人工二次确认（最终确认 `v5`）。这条守住了 B13"只认证据不认推测"。
5. **代价写清**：把"模板放 skill 而非系统提示词"换算成**每请求省约 9.1k token**，
   并注明是粗估口径、未用 `estimate_tokens`（工具口径不适用）。
