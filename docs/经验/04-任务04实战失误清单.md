## 一、本次失误（按代价排序）

### F1　任务书给的接线写法在新机制下**必然失效**，而它引用的"官方先例"是**另一种机制**

- **现象**：任务书 §一 建议 `prefix: !!js "...readFileSync(new URL('PROMPT.md', baseUrl), 'utf8')"`，
  依据是"官方创造模式里用过同一个机制（`presets/cordis/agent.cordis.yml` 的 `new URL('skills/', baseUrl)`）"。
  照抄的结果是：**读不到文件**，且**不一定报错**（在配置求值阶段抛异常 → 整个 preset「加载失败」，模式在选择器里消失）。
- **证据**（原始输出，实施记录 §2.3）：
  ```text
  FAIL | A1 相对 baseUrl 读 PROMPT.md（任务书建议写法）
       => ENOENT ENOENT: no such file or directory, open '<DSH_HOME>\profiles\desktop\PROMPT.md'
  ```
  源码证据（只读）：
  - `cordis-plugin-loader/lib/index.js:289` —— `!!js` 的求值器是 `new Function("ctx","expr","with (ctx){return eval(expr)}")`，
    所以 `baseUrl` **确实在作用域里**；
  - 但 `baseUrl` 的值是 **profile 配置目录**：`dsh-app-boot/lib/index.js:1529`
    `ctx.baseUrl = pathToFileURL(dirname(absoluteConfigPath)).href + "/"`；
  - 官方那份能用，是因为**它是被 include 的子树**：`dsh-app-boot/lib/index.js:140`
    `this.ctx.baseUrl = new URL(".", pathToFileURL(this.filename)).href`（`Include` 把自己的目录设成子树 baseUrl）；
  - 而**本 bundle 的 `cordis.patch.yml` 是「补丁层」**：`dsh-app-boot/lib/index.js:845-870`
    把它读出来当 patch list，再 `composeEntries` 应用到 profile 根 entry list → 插入的行继承的是 **profile 目录**。
- **根因**：把"某个官方文件能用某机制"当成了"**我这份文件**也能用"。
  两者**文件的角色不同**（include 子树 vs 补丁层），而 `baseUrl` 的含义随角色变化。
  **同一行 YAML 文本，角色不同，语义就不同。**
- **教训**：**"官方先例"只证明那一个文件在那一个角色下可行，不证明机制通用**。
  引用先例前，先回答一句：**我这份文件是被 include 的子树，还是被当作补丁层？**（两者的 baseUrl 不同。）
- **模式约束建议**：把任务 03 的候选 20 扩写成两条：
  ① 落点/挂载类结论必须实测（原样）；
  ② **引用"官方/样板先例"时，必须同时说明"先例里那份文件扮演的角色"与"我这份文件扮演的角色"是否相同**；
  角色不同就不得直接照抄，必须自己跑一次。

### F2　硬约束集合内部会出现「举例」与「禁令」的张力

- **现象**：任务书 §三 第 1 项 ⑨ 用「本机 PowerShell 是 5.1、F: 盘是 FAT32」**举例**说明"本机工具版本有特殊性时写进文档"；
  而同一份任务书的附录 B 第 6 条 ⑩ 又**禁止**把某一台机器的具体值写进模式自身的系统提示词。
  两条并列时，照 ⑨ 的举例写 → 违反 ⑩；照 ⑩ 写 → 看起来"没按 ⑨ 举例"。
  同类还有 ⑪ 的括号里带着一个本机绝对路径（`<REFERENCE_PROJECT_PATH>`），
  而 ⑪ 自己最后一条又要求"产出物里不得出现参照项目的路径"。
- **证据**：任务书 §三 第 1 项 ⑨ / 附录 B ⑩ / 附录 B ⑪ 三条并列原文（本仓库 `docs/工作流程/04-模式系统提示词正文.md`）。
- **根因**：约束是**分批追加**的（⑩ 是"要开源给所有人用"这条认识成立之后才加的），
  早先写下的**举例**没跟着改成泛指，于是同一个文件里同时存在"举例值"与"禁止值"。
- **教训**：**"举例"与"禁令"冲突时，取禁令**——禁令通常是后加的、且是**禁止性**表述；
  举例只是帮助理解，删掉它不损失规则语义，而写进禁止项会**实际造成伤害**（把个人路径/本机事实开源出去）。
  处理时必须**登记为偏离并请人工确认**，不能静默改写。
- **模式约束建议**：出稿前对约束集做一次**冲突扫描**，重点查三类张力：
  ① 举例 vs 禁令（本条的形态）；② 通用机制 vs 具体值；③ "必须写 A" vs "不得出现 A"。
  发现冲突 → **按禁令实现 + 逐条登记 + 请人工裁决**，不静默取舍。

### F3　校验器不注册 `!!js` 标签，它报的警告容易被误读成"文件有问题"

- **现象**：`validate-bundle.cjs` 对本次新写的 `prefix: !!js "…"` 报
  `YAMLWarning: Unresolved tag: tag:yaml.org,2002:js at line 63, column 23`，
  连既有的 `disabled: !!js …` 也一起报。看起来像"YAML 写坏了"。
- **证据**（原始输出，实施记录 §4）：
  ```text
  (node:11844) [TAG_RESOLVE_FAILED] YAMLWarning: Unresolved tag: tag:yaml.org,2002:js at line 63, column 23
  === 合计：全部 PASS（FAIL 数 0） ===
  ```
  该脚本用 `<DSH_INSTALL>\node_modules\yaml`（不注册 `!!js`）；运行方用的是 `js-yaml` + `JsExpr`
  （`dsh-app-boot/lib/index.js:17` `new yaml.Type("tag:yaml.org,2002:js", …)`）。
- **根因**：与任务 03 的 F4（自造校验器的隐含假设）**同族**，但换了形态：这次不是 `FAIL` 而是 `WARNING`，
  而且"警告"比"FAIL"更容易被当成噪音忽略或当成缺陷误判。
- **教训**：**警告与 FAIL 一样要分型**：先问"这条警告是哪一方的假设造成的"。
  能用**运行方自带的解析器**复核的，就用它复核（本次改用 `loadOverlayPatches`，警告消失且拿到结构化结果）。
- **模式约束建议**：把任务 03 的候选 23 扩写为：
  「自造校验器报 **FAIL 或 WARNING** 时，先定位'是哪条假设'再决定改产物还是改校验器；
  能用运行方自带的解析/校验入口复核的，一律用它复核一遍再下结论。」

### F4　对照实验的"对照组"复用了"实验组"的变量，差点得出反向结论

- **现象**：写接线验证脚本时，把"对照组"（任务书建议的相对读法）写成了
  `evaluate({baseUrl}, prefixNode.__jsExpr)` —— 而 `prefixNode` 里装的正是**已改好的表达式**。
  于是输出变成 `B FAIL —— 相对读法竟然成功了（与预期不符）`：
  **"实验组"与"对照组"是同一段代码**，脚本自己制造了一个假结论。
- **证据**（原始输出，第一版脚本）：
  ```text
  B  FAIL —— 相对读法竟然成功了（与预期不符）
  ```
  改成两条**独立字面量**后（`"...readFileSync(new URL('PROMPT.md', baseUrl), 'utf8')"` vs 从解析结果取出的表达式）：
  ```text
  2.1 相对 baseUrl 读法 | FAIL（预期失败）| ENOENT … open '%USERPROFILE%\.dsh\profiles\desktop\PROMPT.md'
  2.2 实际接线表达式   | PASS | 读到 12253 字符 | 与 PROMPT.md 逐字一致 = true
  ```
- **根因**：对照实验的心智模型是"两段**不同的**代码、同一个环境"，而实现时图省事复用了变量。
  脚本不会报错——它只是安静地给出**错方向的结论**。
- **教训**：**对照实验的两组必须是两条独立字面量**；"对照组"严禁复用"实验组"的变量。
  输出里要能一眼看到**两组各自的代码原文**（本次修正版就是把两条表达式都印出来）。
- **模式约束建议**：凡"改前 / 改后""对照 / 实验"类的实验，脚本必须把**两组各自的输入原文**打印出来；
  只打印结论不打印输入的实验，不得作为证据。
