# v1.2.0 · 取消提问轮数上限，改为版本迭代询问法

> 本文件是 Release 正文草稿（仓库惯例：每版 Release 留一份成文，见 `07-Release草稿-v1.0.0.md` / `10-Release草稿-v1.1.0.md`）。

**不改功能，只改"怎么问"。** 原来那个「每轮 3–10 题、最多 6 轮」的固定上限**整条删除**，
换成按版本推进的**版本迭代询问法**：**每版本每轮 3–9 题、每版本最多 9 轮**
（单版本下限 = 3 题 × 1 轮 = **3 题**，上限 = 9 题 × 9 轮 = **81 题**）。
**版本数量不设上限** —— `9×9` 只约束"每版每轮题数 × 每版轮数"，不约束版本个数。

顺带把并行规划写实：允许**互不依赖的任务并行开工**，但并行批次后面**必须单列一个「组装验收」任务**，
否则视为规划不合格。

## 本版内容

- **插件** `presets/task-planning-bundle/plugins/token-estimator/index.js`
  - **本版一行未改**（只动提示词与文档）。发布前做了一次回归，`node --check` 通过。

- **系统提示词** `presets/task-planning-bundle/PROMPT.md`（哨兵 `v9 → v10`）
  - **§二 整节重写为版本迭代询问法**：流程由「解析需求 → 多轮提问」四步改为五步 ——
    **解析需求 → 版本迭代规划表（等使用者确认）→ 逐版本多轮提问 → 每版需求确认书 → 规划**。
  - **版本迭代规划表**是新增的第一步且**必须等确认**：固定五列
    （版本 / 阶段名 / 一句话目标 / 前置版本 / 能否与其它版本并行），划分依据是**能力实现阶段**，
    默认三段式 **骨架 → 核心能力 → 收尾验收**；使用者说"切得不对"就先改划分，不许直接开始问。
  - **节奏口径**：原「每轮 3–10 题、最多 6 轮」**整条删除**，改为 **每版本每轮 3–9 题、每版本最多 9 轮**。
    9 轮问完仍不满 9/9 的，剩余项写「未知，按默认假设 X」，**不许开第 10 轮**；
    只剩 1–2 项的**不单独开一轮**（会破 3 题下限），直接用默认假设收口。
  - **每个版本各一份 9 项需求清单**，逐版本填到 9/9；后面版本沿用前面结论时**必须复述结论**，不许只写「同上」。
  - **版本闸门**：本版本确认书通过 → **自动进下一版本**，不再问「要不要继续」；全部版本问完后
    再给**一页总确认书**，确认后才进入规划。
  - **喊停语义升级**：使用者说「停，开始规划」**对整个项目生效**，不再只对当前版本生效；
    已确认版本照常出确认书，问到一半的版本用默认假设补齐并标注「未确认」，没轮到的版本在总览标「暂不规划」。
  - 进度显示由「已清楚 x/9」改为「**第 N 版本 · 已清楚 x/9**」。
  - **硬约束 ④** 补一句：版本迭代下 = **每个版本各填满一份** 9 项清单。
    **硬约束 ⑦ 扩容**：允许并行，但必须 ① 在依赖图里标出哪些可并行并给理由；
    ② **改同一文件的任务不许并行**，必须串行；③ **单列一个「组装验收」任务**排在并行批次之后，
    负责合并冲突 / 接口对齐 / 重复实现 / 各自验收相互抵消的检查。**缺 ③ 视为规划不合格。**
  - **§五.7** 新增：`docs/工作流程/00-总览与使用说明.md` 必须有「**版本迭代规划**」小节
    （版本表 + 版本依赖图 + 并行说明三件齐全），缺这一节视为不合格。
  - **§十一** 增加：按版本分组给顺序、**必须画版本依赖图**（并列括号 = 可并行，并行线末端必须收到组装验收任务）、
    可并行时**同时开的会话不超过 3 个**；**§十二** 自检项 6/7 同步扩写；**§十五** 提问流程与估算口径改写。
  - **体量守住上限**：**389 行**（要求 ≤ 400）、**9887 汉字**、15 个章节、12 条硬约束 ①–⑫ 齐全。

- **文档**
  - `presets/task-planning-bundle/skills/planning-templates/SKILL.md`：骨架一新增【必须】小节「版本迭代规划」；
    任务总清单表新增「可并行?」列、改按版本分组；依赖图样例改为带并行分支 + 组装验收；
    共用硬规则新增第 11 条「并行必须收口」；落盘前核对 **10 → 11 条**。
  - `README.zh.md` / `README.en.md`：使用流程按版本迭代重写（版本规划表 → 逐版本提问 → 每版确认书 → 总确认书），
    产出表补「版本迭代规划表」一行，补「可并行任务可同时开 2–3 个会话、但必须过组装验收」。
  - `presets/task-planning-bundle/README.md`：文件清单标注哨兵 `v10`、小节数更正为 15。
  - `presets/task-planning-bundle/cordis.patch.yml`：新增一行 `touch` 记录（哨兵 `v9 -> v10`，用于触发 preset 重组）；
    **插件行一行未动**（仍是 16 行）。
  - `docs/实施记录/11-版本迭代询问法.md`：本版的需求裁决、改动清单、设计取舍与两套验证的完整留档。

**没动的**：

- **硬约束 ① 原文一字未改**（「只规划不执行」）。本次改动本身属于"修改本模式自己的文件"，
  按使用者裁决走**会话内口头例外**，不写进提示词正文，所以自指边界保持原样。
- **token 阈值口径不变**：仍是「单任务预估 > 6000 万 token → 必须二次拆分」+「估算表必须落盘」。
- `plugins/token-estimator/index.js`、`package.json`（仍是 `0.1.0`）、`presets/task-planning/`（0.1.x 旧机制留档）未动。
- 历史记录（`docs/实施记录/`、`docs/验收报告/`、`docs/经验/`、`docs/工作流程/` 任务书）记录的是当时口径，
  **不作追改**。

## 升级（DSH 0.2.x，实测路径）

> 本版**只改提示词与文档**，且已同步改过 `cordis.patch.yml`（新增 `touch` 行），
> 所以**不必卸载重装，重启即可**让 preset 重组。

1. **不需要卸载重装**。若你更习惯覆盖安装，也可在插件管理器重新粘贴本仓库 `presets/task-planning-bundle` 的**绝对路径**再装一次
2. **完全退出桌面端**（不是关窗口），再启动
3. 新开会话 → 模式选择器选「**任务规划**」→ 问「**当前哨兵值是多少？**」，
   应逐字回答 `<!-- PROMPT-SENTINEL: v10 -->`
4. （可选，行为面）说一句「我想做个记账小工具」，看它是否**先给「版本迭代规划表」并问划分对不对**，
   而不是立刻开始问第一题 —— 这是本版新流程的行为判据

> 答 `v9` 或答不出 = 没生效。此时**不要反复重启试**，按 `presets/task-planning-bundle/README.md`
> 第四节第 7 条排查（关键是确认改的是 `cordis.patch.yml`，而不只是改了 `PROMPT.md`）。
> 安装报 `ERR_PNPM_UNEXPECTED_STORE` 的修法也在同一份 README。
