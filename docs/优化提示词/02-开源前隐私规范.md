# 02-开源前隐私规范（开源前必读 · 个人信息零泄露）

> 本文件是《dsh-task-planning-mode》的公共约束之一，与 `01-通用规范.md` 同级、同样适用。
> **适用时机**：只要最终程序**有开源需求**（推 GitHub / 发 npm / 交付给外部 / 上传到任何公开位置），
> 开源**之前**必须过本规范的门禁。没有开源需求的项目不强制，但建议照做。
> **本规范约束的是「最终程序」，不是「本插件自己」**：本插件规划出来的项目，同样要遵守它。
> 用户补充区在文末。

---

## 一、一条硬规则

**最终程序只要有开源需求，开源前必须保证个人信息零泄露。**

- 「个人信息」指**能定位到具体自然人或具体机器**的信息：真实姓名、登录用户名、邮箱、手机号、社交账号、
  机器 SID / 主机名、家目录绝对路径、内网路径，以及各类凭据（API key、token、私钥、口令）。
- **个人签名（署名）允许，但不强制**：可以写作者名 / 昵称 / 主页链接，前提是**你本人愿意公开它**。
  不想公开就用中性署名（例如 `<项目名> contributors`）。**默认一律用中性署名**。
- 判据不是「我有没有写」，而是：**陌生人拿到这个仓库，能不能顺着它找到我、或者拿到我的凭据。**

---

## 二、要查什么（五类，逐类过）

| 类别 | 典型物 | 为什么危险 | 处理 |
|---|---|---|---|
| ① 凭据 | API key、access token、私钥（`.pem`/`id_rsa`）、`.env`、数据库口令、cookie | 拿到即可冒用，部分还能直接改你的代码 | **先吊销**，再从工作区**和 git 历史**里清掉；不能只删最新提交 |
| ② 身份 | 邮箱、真实姓名、Windows/macOS 登录用户名、机器 SID、手机号 | 可被反查、被骚扰、被社工 | 占位化 |
| ③ 路径 | `%USERPROFILE%\…`、家目录、内网路径、NAS 路径、公司项目路径 | 路径里往往嵌着用户名；也暴露你的目录结构 | 占位化，或改写成仓库内相对路径 |
| ④ 元数据 | **git 提交的作者 / 提交者姓名与邮箱**、提交信息、tag 签名、文件里的作者字段 | 每一次 commit 都会公开一次，**最容易被忽略** | 开源前重写历史换中性身份，或改用 GitHub `noreply` 邮箱 |
| ⑤ 二进制与图片 | 截图、录屏、日志、压缩包、`.db`、Office 文档属性 | 文本扫描器扫不到，却常含用户名 / 路径 / 会话内容 | **必须人工看**，或换用干净的重制件 |

> 经验：③ 和 ④ 是实际最高频的泄露源。① 一旦出现就是事故级，先吊销再谈清理。

---

## 三、占位符约定（统一用这套，别自创）

| 原物 | 占位符 |
|---|---|
| 家目录 | `%USERPROFILE%`（Windows）/ `$HOME`（macOS、Linux） |
| 登录用户名 | `<user>` |
| 邮箱 | `<EMAIL_REDACTED>` |
| 机器 SID | `<USER_SID>` |
| 仓库根绝对路径 | `<REPO>` |
| 各类密钥 | `<API_KEY_REDACTED>`、`<GITHUB_TOKEN_REDACTED>` … |
| 参照项目 / 他人项目 | `<REFERENCE_PROJECT>` |

内部记录（`docs/实施记录/`、验收报告）同样要占位化——它们是随仓库一起公开的。
占位化**不算篡改证据**：只要保留「原文是什么形状、结论是什么」，可复核性不受影响。

---

## 四、流程（五步，缺一不可）

0. **先定公开范围**：哪些文件会进公开仓库（= git 跟踪的文件），哪些是内部产物（不跟踪，加 `.gitignore`）。
   内部产物（自测 / 验收 / 沙箱报告 / 另一个项目的残留）**不要**随仓库发布。
1. **工作区扫描**：`node tools/privacy-scan.mjs --all`
2. **历史扫描**：同一条命令默认已包含**全部提交历史**（作者 / 提交者身份 + 提交信息 + 每个历史版本的文件内容）。
   **这一步不能省**——删掉最新提交里的密钥，历史里还在；改掉现在的邮箱，旧 commit 里还在。
3. **自动占位化**：`node tools/privacy-sanitize.mjs --all`（先加 `--dry-run` 预览要改什么）
4. **人工复核扫描器覆盖不到的部分**（截图 / 图片 / 二进制 / 文档属性 / tag 签名），并把结论写进验收报告。

---

## 五、工具与门禁

| 工具 | 作用 |
|---|---|
| `tools/privacy-scan.mjs` | 只读扫描；输出 `block` / `warn` 两级结论；有 `block` 命中时退出码 1 |
| `tools/privacy-sanitize.mjs` | 按同一套规则把文本占位化（**幂等**，重复跑无副作用）；`--dry-run` 只预览 |
| `tools/privacy-check.ps1` | 门禁包装：`pwsh -File tools/privacy-check.ps1`（可加 `-All` / `-WorktreeOnly`） |
| `tools/privacy-rules.json` | **通用规则**（随仓库公开） |
| `tools/privacy-local-rules.json` | **本机字面量**（被 `.gitignore` 排除，**绝不入库**） |

**规则必须分两层**：通用规则（邮箱格式、`sk-` 前缀、`%USERPROFILE%`、SID 格式、本机登录用户名占位符 `{{USERNAME}}`…）
可以入库；本机的具体值（真实用户名、邮箱、盘符布局）放本地规则文件。
**不能把真实值写进公开仓库**——否则扫描器自己就泄露了它要防的东西。

**门禁判据**：
- `block` 命中 **0**（工作区 + 全部历史）；
- 内部产物**没有被 git 跟踪**；
- `warn` 允许存在，但**每一条都要有人工结论**（写进报告）。

## 六、验收清单（照抄进验收报告）

- [ ] `node tools/privacy-scan.mjs` 退出码 0（block 命中 0）
- [ ] **历史扫描同样 0 命中**，含作者 / 提交者身份
- [ ] 内部产物未被跟踪，`.gitignore` 有对应条目
- [ ] 截图 / 图片 / 二进制 / 文档属性已人工看过，结论写进报告
- [ ] 若发现真凭据：**先吊销**，再清理；报告写明吊销时间与影响范围
- [ ] 署名形态写明：中性署名，或使用者明确同意公开的个人署名
- [ ] 重写历史的话，记录「旧 hash → 新 hash」的对照或至少写明「hash 已变，旧引用失效」

---

## 七、常见问题

- **只删最新提交行不行？** 不行。历史里还在，`git log -p` 一翻就出来。
- **仓库还没推送，要不要重写历史？** 要，而且**现在最省事**。一旦推送，别人可能已经 clone / fork，
  再改就得强推并通知所有使用者。
- **重写历史会改变 commit hash**：文档里引用过的旧 hash 会失效，重写后要同步更新或明确标注失效。
- **扫描器报 `warn` 但看着没事？** 正常。`warn` 是「请人工看一眼」，
  例如 `D:\.pnpm-store\…` 这种只有盘符、没有身份信息的路径。
- **中文文件名 / 内容会不会误报？** 不会。规则按**内容**匹配，与文件名和语言无关。
- **`.gitignore` 加了就一定安全吗？** 不。已经被跟踪过的文件，加 `.gitignore` 不生效，必须先 `git rm --cached`。
- **发现密钥已经推上去了怎么办？** 顺序永远是：**先吊销 / 轮换密钥** → 再清历史 → 再强推 → 再通知。
  清历史不能替代吊销，因为对方可能早已 clone。
