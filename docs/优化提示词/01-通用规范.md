## 一、你在做什么

`dsh-task-planning-mode` 是 DeepSeek Harness（DSH）的一个新模式插件：**「任务规划」模式**。
它给"完全不懂目标行业、但明确知道自己想要什么效果"的使用者用：把想法问清楚 → 拆成可执行的
规划与提示词 → 告诉他按什么顺序做。**它自己不实现任何东西。**

本项目的交付物：模式本体（agent preset）、模式系统提示词、token 估算器本地工具插件、
规划文档模板 skill（含流程图模板）、开源仓库与文档。

## 二、铁律（违反任何一条 = 本次执行失败）

1. **范围围栏**：只做任务文件里列出的事。发现相邻问题（bug、坏味道、"顺手就能改"）→ **写进报告，不许改**。
2. **先读后改**：改任何文件前先 `read` 它；定位用 grep。**禁止凭训练记忆猜 DSH 的内部 API、
   配置字段、服务名**——本项目所有约定以 `docs/调研/` 的一手证据与本机 `node_modules` 源码为准。
3. **一步一验**：每个可独立验证的步骤做完立刻验证；失败即停、如实报告，**禁止静默跳过或放宽验收标准**。
4. **数字说话**：所有"能用/更快/更省"的结论都要附证据（命令 + 输出、文件路径 + 行号、工具调用返回）。
   禁止"理论上应该可以"式断言。
5. **一次会话一个任务**：完成即提交、回写进度、写报告；不要在一个会话里连做多个任务。
6. **提交纪律**：提交信息格式 `[任务NN] 一句话描述`（NN 用两位数字，例如 `[任务03] token估算器插件`）；
   本轮更新用 `[v1.3.0-NN] 一句话描述`。
   一个任务可拆多个原子提交，但每个提交都必须是"可加载、不 broken"的状态。
7. **冲突上报**：现实与规划冲突（行号漂移、结构不同、前提不成立）→ **停下来**，把冲突写进报告交人工裁决；
   不许自行改规划、也不许硬做。
8. **路径与工具约定（本机特殊性，必须遵守）**：
   - 本项目在 **D: 盘**（NTFS）工作：`<REPO>`。
   - **F: 盘是 FAT32**，不支持硬链接。DSH 写文件时用"临时目录 + 硬链接"做原子替换，
     所以**在 F: 新建文件的写入（含 `write` 工具）会直接报错**
     （已实测：`EISDIR: illegal operation on a directory, link '...tmpdir\...' -> '...'`）。
     `edit` 在 F: 的失败路径**未实测**（其实现可能走 ReplaceFileW/rename），本项目不依赖它。
     结论：**本项目的文件一律写在 D:（NTFS）**，不往 F: 写。
   - 本机 PowerShell 是 **Windows PowerShell 5.1**：`Set-Content -Encoding UTF8` **会写 BOM**；
     需要无 BOM 时用
     `[System.IO.File]::WriteAllText($path,$text,(New-Object System.Text.UTF8Encoding($false)))`。
   - **反过来：`.ps1` 脚本文件必须存成 UTF-8 with BOM（带 BOM）**。PS 5.1 读脚本时**无 BOM 就按系统 ANSI（本机 GBK）解码**，
     含中文的脚本会直接语法错误（实测原文：`Unexpected token 'DSH' in expression`、
     `The string is missing the terminator: "`；控制台里中文显示为 `鐜锛?` 之类乱码）。
     即本项目两种编码约定**方向相反**：**`.md` / `.js` / `.json` / `.html` 用无 BOM，`.ps1` 用带 BOM**，不要套用。
     改完 `.ps1` 后复核文件头三字节是不是 `EF BB BF`（见 `docs/经验/06-任务08实战失误清单.md` F1）。
   - **本机没有全局 `dsh` 命令**（`where.exe dsh` 未命中）；profile 的变更靠桌面端插件管理器，
     或手工改 `cordis.patch.yml` 后**重启 DSH**。preset 的改动**新开会话**生效。
   - 官方安装目录 **只读**：`<DSH_INSTALL>\node_modules\@deepseek-ai\...`、
     `%USERPROFILE%\.dsh\profiles\node_modules\@deepseek-ai\...`。预设升级会覆盖 shipped preset，
     改坏了会连带影响其它模式。
   - 用户层预设目录：`%USERPROFILE%\.dsh\.agent-presets\task-planning\`（这是我们的安装目标）。
   - npm 官方源当前可直连；国内变慢时用镜像 `https://registry.npmmirror.com/` 并在报告中记录来源。
9. **文档语言与格式**：所有新增文档、注释、报告一律中文；规划文档格式对齐
   `docs/调研/04-规划文档格式.md` 的结论（编号规则、5 字段信息头、五态台账、报告结构）。
10. **不许夸大**：未实测的平台/能力，文档里必须写"未实测"或"不支持"；
    机制上属于"推导"而未经运行时验证的结论，必须标注"推导，未验证"。
11. **人工验证与 AI 的边界**：凡需要"新开会话 / 切换模式 / 重启 DSH / 在 UI 里点选 / 在浏览器里操作"
    的验证，**一律由人工执行**。AI 只能：给出精确步骤 → 等人回填**原始输出** → 如实写入报告。
    **禁止自己填写、推测或"合理补全"人工验证的结果**；报告里要标明"本项由人工执行，执行人：<用户>"。
12. **产物边界（工作区内）**：本项目产出的所有文件——规划文档、报告、实施记录、preset 文件、
    自测与 Demo 产物——**必须写在 `<REPO>` 之内**。
    **唯一例外**：任务 01/02/03/05 明确要求的"把 `presets\task-planning\` 复制到用户层
    `%USERPROFILE%\.dsh\.agent-presets\task-planning\`"这一安装动作（目标路径固定、只许覆盖该目录）。
    除它之外，禁止写任何工作区之外的路径，尤其禁止写官方安装目录
    （`<DSH_INSTALL>\...`、`%USERPROFILE%\.dsh\profiles\...`）。
    **`<REFERENCE_PROJECT_PATH>` 只是命名与格式的参照项目，不是要使用的项目**：
    不许在其中创建/修改任何文件，不许把它当成目标项目，产出物里也不得出现它的路径。
13. **开源前隐私门（本仓库自身适用，且是本插件对外承诺的规范）**：本仓库要开源，因此**发布之前**必须过隐私门。
    细则见 `docs/优化提示词/02-开源前隐私规范.md`，工具见 `tools/privacy-scan.mjs` / `tools/privacy-sanitize.mjs` /
    `tools/privacy-check.ps1`。要点：① 工作区与**全部提交历史**双向扫描（提交历史的作者 / 提交者身份也算公开内容）；
    ② 真实姓名、登录用户名、邮箱、机器 SID、家目录绝对路径、各类凭据一律占位化或清除；
    ③ 扫描器扫不到的截图 / 图片 / 二进制必须人工过一遍；④ 真凭据**先吊销，再清理**；
    ⑤ **通用规则入库、本机字面量不入库**（`tools/privacy-local-rules.json` 已被 `.gitignore` 排除）；
    ⑥ 内部验证产物（自测 / 验收 / 沙箱报告）不得随仓库公开。**个人签名允许但不强制**。
14. **历史记录只归档不追改**：`docs/实施记录/`、`docs/经验/`、`docs/调研/`、`docs/验收报告/01~08`
    里的数字与结论代表**当时的真实口径**，**不许为了让它们"看起来一致"而改写**。
    口径变了就在新文件里说明，不改旧文件。（例：`docs/实施记录/03` 里 4.64M–14.49M 是 ×20 之前的标定，
    自 v1.3.0 起一律以校准后数字为准，但那段历史**保持原样**。）

## 三、收尾四步（每个任务完成时按顺序做）

1. **提交**：按铁律 6 的格式 commit。
2. **回写进度**：更新 `docs/优化提示词/执行进度.md` 中本任务那一行（状态、提交哈希、关键数据）。
3. **写文档（两个目录分工不同，不要混）**：
   - **`docs/验收报告/NN-报告.md`（必写）**：结论性报告 = 做了什么（含偏离计划之处）+ 验证结果
     （逐条验收标准 ✅/❌ + 证据）+ 关键数据 + 遗留问题 + 给下一个任务的注意事项 + 人工判定栏。
     模板见 `docs/验收报告/00-验收报告模板.md`。
   - **`docs/实施记录/NN-<短名>.md`（按需）**：原始证据留档 = 命令与原始输出、探测结论（含 file:line）、
     接线记录、中间实验数据。任务文件写了要产出的，必须产出；没写的可省略。
   - **`docs/经验/NN-*.md`（有失误就必写）**：把本次的失误**提炼成可迁移的教训**，每条写
     「现象 → 证据 → 根因 → 教训 → 对模式的约束建议」。
     **为什么必写**：本项目就是用「任务规划」模式开发「任务规划」模式本身，
     开发过程踩的坑就是最终模式的养料——写系统提示词时**必须**取用
     `docs/经验/01-任务01实战失误清单.md` 第三节的硬约束候选。
     （本目录含本机路径与项目细节，**不要整段抄进将来要开源发布的模式提示词**，见铁律 8 与用户补充区第 1 条。）
4. **有门就停**：任务标了"验收门"的（06、07、31、32），报告写完后**停下等人工判定**，
   不要自行进入下一个任务。

## 六、v1.3.0 增量补充（做 11/12/13/20/30/31/32/33 时必须一起读）

### 6.1 估算口径（做 11、20 时最重要）

1. **×20 校准是硬口径**：`estimate_tokens` 的静态输出已按 `CALIBRATION_FACTOR = 20` 放大。
   这个系数**只能乘在 `raw` 那一行**，不许改成动 `LOW_FACTOR` / `HIGH_FACTOR`——
   那两个常数的语义是"区间下沿/上沿"，混入标定倍率以后就没人说得清哪个数代表什么。
2. **必须标注**：返回值、渲染文本、所有落盘文档都要出现「**本估算基于 ds4.1f 消耗计算**」。
3. **6000 万阈值不变**，判断口径仍是**单任务 / 单对话**。校准后更容易触发，**这是正确行为**；
   不许为了"少报警"把系数调小或把阈值抬高。
4. **两个「合计」不是一回事**：
   - 估算表里的「合计（保守）」= **该行的高值**（判阈值用它）；
   - 工具返回的 `total` = `(低+高)/2 × 1.5`（另一口径）。
   引用时**必须写清是哪一个**。
5. **±10% 是验收判据**（本轮的取舍）：三组规模的实算值与任务书基准偏差 ≤ ±10% 即通过。
   它能抓"少乘一个 20""多乘一次 1.5"，但**抓不到系数微调**（例如把 20 改成 19）——这是已知局限，不要假装它能抓。

### 6.2 流程与并行（做 12、13、20 时最重要）

1. **流程图是必须产出物**：`docs/工作流程/00-任务执行流程图.html`（编号 `00`，**不是任务**）。
   由 `skills/planning-templates/assets/task-flow.html` **只替换 `window.TASK_FLOW_DATA`** 生成。
2. **`deps` 写节点 `id`，不是编号**（写编号会断线）；**`status` 只取五态之一**（写错会退化成「未开始」）。
3. **状态真相以 `docs/优化提示词/执行进度.md` 为准**：每个任务收尾时两处一起改，不一致时改流程图。
4. **并行批次的两种合法写法**：要么给「子任务切分 + 写入范围 + 汇合方式」（可用子代理），
   要么写「**无子代理，已串行**」。**没有第三种**——标了并行却一个人串行做完还说自己并行过 = 不合格。
5. **并行上限是 2 个会话**（本项目裁决），不是模式默认的 3 个。

### 6.3 收尾交接（做全部任务时都要执行）

1. **每个任务收尾三件事**（缺一视为没做完）：
   ① 回写 `执行进度.md` 本任务行；② **用 `ask_user_question` 把「六、收尾交接」里的决策项逐条问**
   （每题 2–4 个选项、每个选项一句话写清利与弊、推荐项放第一个）；③ 把「下一个任务预计耗时」
   写进台账「关键数据」列并填进流程图对应节点。
2. **不许替使用者决定**，也不许把默认假设当成他的答复。
3. **下一个任务耗时必须给区间 + 依据**（文档字数 / 文件数 / 是否联网 / 是否需人工操作），
   不许只写"大概一会儿"。

### 6.4 发布面（做 30、31、32、33 时最重要）

1. **改完 `PROMPT.md` 或 `skills/` 必须触碰 `cordis.patch.yml`**（追加一条 touch 注释），
   否则 mtime+size 不变、preset 不重组，改了白改。
2. **生效判据只有一个**：重启桌面端 + 新开会话，问「当前哨兵值是多少」，**答 `v11`**。
   文件改了、测试过了，都不算生效。
3. **强推用 `--force-with-lease`**，不许用裸 `--force`。
4. **推送后必须从远端重新克隆回来复扫**——本地干净不等于远端干净。

### 6.5 模式自省规则（任务 13A 新增；做 13A 与 20 时最重要）

2026-11-12 发生了一次严重违规：在有「只规划不执行」硬约束的前提下，直接实现了使用者提出的 5 条更新
（改了 15 个业务文件 / +1998 行，一个问题都没问，还用了子代理并行）。**规则不是不够严，是识别环节失效。**
教训全文见 `docs/经验/07-模式违规执行与旧数字.md`。**执行任务 13A 时，5 条判别式要写进 `PROMPT.md` §一.9~§一.13
与 `SKILL.md`「三、模式自省规则」两处，且两处逐字一致。**

判别式的要点（执行时照抄任务文件里的完整版，这里只作索引）：

1. **边界由产出物类型界定，不由指令明确度界定** —— 只要要写的文件不在 `docs/` 下的规划与提示词里，就是越界。
2. **需求文本里的动词是"要写的内容"，不是"要做的动作"** —— 看到「可以要求用子代理执行」，正确反应是把它写进任务文件的提示词。
3. **违规后的第一动作是停、说明、请裁决** —— 不许自行补救（含"看起来无害"的留档分支）。
4. **每个"现状是 N"都必须有一条当场可重跑的命令** —— 不许引用记忆里的数字。
5. **"不是我造成的"要有归属证据才能写** —— 引用隐私扫描时，`blockFindings` 与 `blockMatches` 必须分别记。

> 这 5 条是 **§一 的子条目，不是第 ⑬ 条硬约束**（12 条是固定结构，不许加）。
> 另外：本项目的 `docs/实施记录/`、`docs/经验/` 是**教训的仓库**，写新模式规则时应当去那里取材
> ——但**只取抽象的判别式，不抄具体文件名、分支名、提交哈希**。
