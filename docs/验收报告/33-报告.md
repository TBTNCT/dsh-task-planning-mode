## 二、推送

**命令原文（逐字）**：

```bash
git push --force-with-lease origin main
```

- 远端：`origin https://github.com/TBTNCT/dsh-task-planning-mode.git`
- 分支：`main`
- **推送前** 远端 `main` = `5886ff39da9ffa31759c650f847e004105d4c1a1`（旧历史，重写前）
- **推送后** 远端 `main` = `31feff39f8155ee4edfc3451334f6a94f9b6ee85`（重写后的干净历史）
- 用 `ls-remote` 独立复核：`refs/heads/main = 31feff3…` 与本地 `HEAD` 一致 ✅

> **一处操作现场说明（如实登记）**：强推命令执行时终端输出为空、且本地跟踪引用 `origin/main` 未刷新（仍显示旧值 `5886ff3`）。
> 未把"无输出"当作失败或成功来推断，而是用 `git ls-remote origin refs/heads/main` **直接问远端**，确认 `main` 已是 `31feff3`。
> 若只看本地 `origin/main`，会误判为"没推上去"；这是本地跟踪引用滞后，不是远端状态。

| `v1.3.0` | 本报告所在提交（`git log -1` 可查） | **新建**（`git tag -a v1.3.0 -m "v1.3.0"`，打在本次收尾提交上） |

**为什么 `v1.3.0` 打在"本报告所在提交"而不是强推时的 `31feff3`**：
写本报告会产生一个收尾提交（任务书第 6 步）。若 tag 先打在 `31feff3`，远端 `main` 随即前进一格，tag 就指向了"离 HEAD 差一个提交"的状态——
版本 tag 应当与发布面（`main` 当前状态）严格对齐。故顺序调整为：**强推 → 远端复扫 → 写报告 → 收尾提交 → 打 tag → 再推 `main` + 推 tag**。
本报告不写死自己的 hash：它记录的就是自己，写死会自我指涉、改一次字就又变一次（口径同 `19-对照表` §4.1）。

## 四、两处偏差（均已由使用者裁决，不自行决定）

### 偏差 A：`git status` 不干净 —— 未跟踪目录 `.workbuddy/`

- **现象**：`git status --porcelain` 输出 `?? .workbuddy/`（44 KB，本会话的工作目录）。已跟踪文件**零改动**。
- **为什么清不掉**：它是运行时会话目录，非仓库内容；`.gitignore` 未排除它（任务 32 报告 §8.2 已登记为已知遗留）。
- **影响评估**：推送的是**提交**而非工作区，未跟踪文件不会进入任何提交，对远端内容**零影响**。
- **裁决（使用者）**：**忽略它，直接推**。不在本任务里改 `.gitignore`——任务书负面清单第 1 条禁止本任务改任何文件。
- **风险**：无隐私风险；若将来误 `git add -A`，会把会话目录带入仓库。留给下一轮处理。

### 偏差 B：`v1.2.0` 的"重建"是空操作 —— 任务书假设与实测不符

- **任务书原文**：「`v1.2.0`（`41e773e`）在重写边界上，需要按对照表重建到对应的新提交」。`33-推送与打标签.md` §三 第 3 步同样要求"删旧 tag、在重写后对应的提交上重新打"。
- **实测**：重写范围是 `41e773e..HEAD`——**不含 `41e773e` 本身**。`19-对照表` §五 也写明「`41e773e` 及其之前共 57 个提交一个字节都没动，hash 不变」。
  `git merge-base --is-ancestor 41e773e HEAD` → 是；`git log -1 41e773e` 内容与 tag 描述一致。**它根本不在重写范围内，没有"对应的新提交"这回事。**
- **若照脚本硬做会怎样**：删除后在同一提交重打，指向不变，但原 tag 说明「v1.2.0 · 取消提问轮数上限，改为版本迭代询问法（哨兵 v10）」会被 `-m "v1.2.0"` 覆盖成光秃秃的版本号——**信息净损失，且删 tag 与重推之间存在一个"tag 不存在"的窗口**。
- **裁决（使用者）**：**不重建，保持指向 `41e773e`**；本任务只做校验并记录理由。

## 六、哪些操作是不可逆的

**一句话**：本任务里**只有强推远端 `main` 这一步不可逆**——它让远端原 `main`（`5886ff3`，重写范围内的 40 个旧提交）从此不可达，唯一退路是任务 31 的 bundle 全量备份（见 `19-对照表` §一 / §八）；
打 tag、推 tag、写报告、收尾提交都是可逆的（tag 可删可重打，报告可改，提交可再提交），但它们**修正不了已被覆盖的远端历史**。
