## 四、关键设计取舍（为什么这么做）

### 4.1 为什么只重写 `41e773e` 之后

范围小 → 改动面小、hash 变化面小、与已有文档（台账 01–10 行等）的冲突小。
代价是**范围外的命中清不到**——所以先逐提交判定范围，确认 `41e773e` 及更早 0 命中，才敢只重写后半段。
如果当时发现范围外也有命中，本任务会停下来交人工重新裁决，而不是自作主张扩大范围。

### 4.2 为什么必须"先备份再动手"

`filter-branch` 改的是 hash，**不可逆**；而且本次还额外做了 `reflog expire` + `gc --prune=now`（
不这么做，旧对象还能被 `git fsck` 捞出来，等于没清）。旧提交一旦从本地消失，**bundle 就是唯一退路**。
所以流程是：备份 → `git bundle verify` → 在备份克隆里试跑 → 复扫通过 → 才动正式仓库。

### 4.3 为什么额外清 `origin/main` 与 reflog

只重写 `refs/heads/main` 是不够的：`refs/remotes/origin/main` 还指着旧提交，`git rev-list --all` 会把
整段旧历史再扫一遍——**试跑时就踩了这个坑**（复扫仍报 126 处 block，全部来自 origin/main 指向的旧提交）。
所以重写后必须：删 `refs/original/*` → `origin/main` 重指新 HEAD → 清 reflog → `gc --prune=now`。
